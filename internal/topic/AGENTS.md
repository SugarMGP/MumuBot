# AGENTS

本目录负责话题工作记忆：消息归属、摘要刷新、历史话题召回和给 agent 的话题上下文。

## 入口与职责

- `manager.go`：话题管理器、运行队列、启动恢复、消息持久化和上下文组装。
- `assignment.go`：批量话题归属的提示词和模型输出规范化。
- `store.go`：PostgreSQL 数据访问、精确向量与 trigram 的 RRF 召回，承担消息日志、话题线程和不可变摘要版本持久化。
- `prompt.go`：给模型看的话题上下文渲染。

## 语义边界

- 话题工作记忆是主路径能力，不加可关闭开关，也不为主链路补可选兜底。
- 话题归属、摘要和检索只使用原始文本；原始文本为空的消息不进入模型分配队列。
- 模型漏返回、返回非法动作、候选话题无效、新话题编号缺失或模型调用失败时保持真实 pending 并记录日志，等待后续补偿。
- pending 由数据库中尚无最终 `topic_assignments` 的消息表示，不维护第二套内存消息状态。
- 存储层失败要暴露真实错误；只有数据库事务确实写入 `no_topic`、`new` 或 `reuse` 后才算完成，失败记录由恢复循环重新查询。

## 提示词与结构化输出

- 话题归属提示词必须约束模型不要重复返回同一个 `message_key`。
- 如果模型仍重复返回同一个 `message_key`，解析层只接受第一条并保留日志，方便追查模型行为。
- `keywords`、事实、未完事项等列表字段必须按结构体要求返回数组，不要把逗号分隔文本当成列表。

## 修改注意

- 队列压力、关闭中、模型失败都不能伪装成“已处理但无结果”。
- 摘要按当前话题 `topic_assignments.id` 的完成顺序推进；其他话题的 pending 不能阻塞当前话题。
- `topic_summaries` 只保存 `through_topic_assignment_id` 作为水位，话题关系通过 assignment 推导，不重复保存 `topic_id`。
- assignment 恢复、摘要刷新和摘要下沉长期记忆分别运行，长模型调用不能阻塞其他恢复链路。
- Agent 上下文优先加入固定快照中被回复消息所属的话题，再追加最近话题和 RRF 召回，并保持总长度上限。
- Agent 话题召回与话题归属候选统一使用原始消息混合查询，不再依赖回复前模型生成检索词或额外关键词提取器。
- 消息清理不能删除已分配话题的消息。
